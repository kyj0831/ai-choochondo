# PRD — AI 추천도 (ai-discoverability-diagnosis)

> 생성형 AI 검색에서 우리 브랜드가 **발견되는가 · 정확히 설명되는가 · 추천 후보에 오르는가**를
> 공개 정보 기준으로 진단하고, 바로 붙여넣어 고칠 문안까지 주는 서비스.

| 항목 | 내용 |
|---|---|
| 문서 버전 | v0.1 (초안) |
| 작성일 | 2026-08-24 |
| 상태 | 검토 대기 — 하단 [16. 오픈 이슈](#16-오픈-이슈--결정이-필요한-것) 답변 후 확정 |
| 제품 형태 | **독립 신규 제품** (ai-nocutnews와 분리된 별도 서비스·저장소) |
| 이 저장소에서의 위치 | 이 PRD 문서와 [원본 스킬 명세](SKILL.md)만 보관. 구현 코드는 신규 저장소로 |
| 원형 | Genspark에서 작성한 Claude 스킬 `ai-discoverability-diagnosis` |

## 1. 한 줄 정의

**지역 가게·기업·개인 전문가의 공개 정보를 조사해, 생성형 AI 검색(GEO) 관점 7개 축으로 진단하고
점수·원인·복붙용 개선 문안·7일 실행계획까지 한 번에 내주는 자동 진단 리포트 서비스.**

---

## 2. 배경 — 왜 지금인가

검색의 진입점이 "링크 10개를 보여주는 화면"에서 "질문에 문장으로 답하는 화면"으로 옮겨가는 중이다.
ChatGPT·Perplexity·Gemini·네이버 AI 브리핑 같은 생성형 검색에서는 **노출 = 답변 문장 안에 이름이
들어가는 것**이다. 여기서 벌어지는 문제는 기존 SEO와 성격이 다르다.

1. **순위가 아니라 후보 진입이 문제다.** 10위든 30위든 링크는 존재했지만, 생성형 답변은 보통 2~5곳만
   호명한다. 후보에 못 들면 노출이 0이다.
2. **AI는 흩어진 정보를 하나로 못 묶는다.** 홈페이지·인스타·기사·지도 프로필의 소개가 서로 다르면
   AI는 같은 대상을 서로 다른 셋으로 이해하거나, 가장 오래된 설명을 사실로 굳힌다.
3. **당사자는 자기가 어떻게 보이는지 확인할 방법이 없다.** 직접 물어보면 그럴듯한 답이 나오지만,
   그게 다른 사용자에게도 같은 답이 나오는지, 무엇이 근거였는지는 알 수 없다.
4. **고칠 방법을 모른다.** "정보를 정리하세요"는 실행이 아니다. 어떤 채널의 어떤 문장을 어떤 문장으로
   바꿔야 하는지가 나와야 움직인다.

즉 시장에 있는 건 "진단해주는 사람"인데 실제로 필요한 건 **진단 + 원인 + 복붙 문안**이다.
이 제품의 차별점은 진단 정확도 자체가 아니라 **진단에서 실행까지의 거리를 0으로 만드는 것**이다.

### 안 하는 이야기

"AI에 우리를 1등으로 띄워드립니다" 같은 보장은 하지 않는다. 생성형 답변은 비결정적이고 모델·시점에
따라 달라진다. 이 제품이 파는 것은 순위 보장이 아니라 **AI가 참조할 근거를 정돈하는 작업**이다.
이 원칙은 마케팅 카피와 리포트 고지문에도 그대로 반영한다([13. 리스크](#13-리스크와-대응) 참고).

## 3. 목표와 비목표

### 3.1 목표 (MVP 기준)

| # | 목표 | 성공 기준 |
|---|---|---|
| G1 | 이름·지역·업종만 넣어도 5분 안에 진단 리포트가 나온다 | 진단 요청 → 리포트 완료 P50 5분, P90 10분 |
| G2 | 리포트의 사실 주장에 근거 링크가 붙는다 | 사실 주장 중 출처 URL 첨부율 ≥ 90%, 깨진 링크 0 |
| G3 | 지어내지 않는다 | 샘플 감사에서 미확인 정보의 사실 서술(메뉴·가격·경력·고객·수상) **0건** |
| G4 | 받은 문안을 그대로 쓸 수 있다 | 리포트 수령자의 채널 반영률 ≥ 40% (7일 후 재진단 시 문안 일치 검출) |
| G5 | 고치면 점수가 오른다 | 개선안 적용 후 재진단 시 종합 점수 평균 +12점 이상 |
| G6 | 3개 대상 유형을 모두 지원한다 | 지역 가게·매장 / 기업·브랜드 / 1인 크리에이터·전문가 전 유형 리포트 생성 |

### 3.2 비목표 (MVP에서 안 함)

- **순위 보장·상위 노출 대행.** 진단과 문안 제공까지가 제품이다. 실제 채널 수정 대행은 v2 이후.
- **ChatGPT 웹 UI 자동 조작·크롤링.** 약관 위반 소지. 측정은 공식 API와 공개 웹 조사로만 한다.
- **자동 반영.** 사용자 채널(홈페이지·인스타·지도)에 직접 쓰기 권한을 받지 않는다.
- **경쟁사 비교 리포트.** v1.5 이후. 타사에 대한 부정적 평가를 자동 생성하는 건 법적으로 위험하다.
- **다국어.** 한국어 대상·한국어 리포트만.
- **모바일 앱.** 반응형 웹으로 충분하다.

## 4. 타깃 사용자

3개 유형을 **동시에 지원**한다. 유형에 따라 조사 대상 채널과 진단 강조점이 달라지므로,
진단 파이프라인은 유형별 분기를 1급 개념으로 갖는다.

### 유형 A — 지역 가게·매장
- **예:** 동네 베이커리, 필라테스 스튜디오, 정형외과, 인테리어 시공사
- **아픈 지점:** "○○동 브런치 추천"에 안 뜬다. 지도 정보와 인스타 소개가 다르다. 폐업한 옛 지점이 계속 나온다.
- **진단 강조축:** 검색 존재감(지역+업종+상호 동시 검출), 정보 최신성, 채널 간 일관성
- **주요 채널:** 네이버 플레이스 · 카카오맵 · 구글 비즈니스 프로필 · 인스타 · 배달/예약 플랫폼 · 블로그 리뷰

### 유형 B — 기업·브랜드
- **예:** B2B SaaS, 제조사, 소비재 브랜드, 로컬 프랜차이즈 본사
- **아픈 지점:** "무슨 회사인지" 한 문장 정의가 안 된다. 보도자료와 홈페이지 설명이 다르다. 경쟁사만 호명된다.
- **진단 강조축:** 설명 정확도, 차별점, 신뢰와 권위
- **주요 채널:** 공식 홈페이지 · 회사소개/IR · 보도자료 · 링크드인 · 채용공고 · 고객 사례 · 언론 기사

### 유형 C — 1인 크리에이터·전문가
- **예:** 강사, 작가, 컨설턴트, 유튜버, 개원 전문의
- **아픈 지점:** 이름·활동명·브랜드명이 따로 논다. AI가 동명이인과 섞는다. 경력은 많은데 정체성이 흐리다.
- **진단 강조축:** 채널 간 일관성(동일인 식별), 설명 정확도, AI 추천 질문 적합성
- **주요 채널:** 개인 사이트/링크허브 · 유튜브 · 인스타 · 브런치/블로그 · 강연 소개 페이지 · 출간 도서 · 인터뷰

> **유형 C 주의:** 실명 개인이 대상이므로 공개 정보만 다루더라도 리포트의 **외부 공유는 본인 확인 이후**로
> 제한한다. 상세는 [13.4](#134-개인정보와-명예).

### 4.1 구매 결정자와 사용자

| 유형 | 결정자 | 실제 사용자 | 구매 동기 |
|---|---|---|---|
| A | 사장 본인 | 사장 또는 매장 SNS 담당 | 손님이 안 온다 |
| B | 마케팅/홍보 팀장 | 실무 마케터 | 브랜드가 잘못 설명된다 / 경쟁사만 언급된다 |
| C | 본인 | 본인 | 제안·섭외가 안 들어온다 |

## 5. 핵심 사용자 여정

```
[랜딩] "우리 가게, AI가 추천해줄까?"
   │  상호 + 지역 입력 (30초)
   ▼
[무료 간이 진단] 60초 이내, 종합 점수 + 한 문장 진단 + 치명적 문제 1개 공개
   │  "나머지 6개 축과 개선 문안 보기" → 결제 또는 로그인
   ▼
[정보 보강] 홈페이지·SNS·기사 링크 추가 입력 (선택, 넣을수록 정확)
   │
   ▼
[정밀 진단 실행] 비동기 3~7분. 진행 상황 실시간 표시
   │  ① 자산 수집 → ② 질문 세트 생성 → ③ AI 응답 측정 → ④ 7축 채점 → ⑤ 문안 생성
   ▼
[리포트] 11개 섹션. 근거 링크 · 복붙 버튼 · PDF · 공유 링크
   │
   ▼
[7일 실행 계획] Day 1~7 체크리스트. 완료 체크 시 진행률 표시
   │  Day 7 → "재진단하기" 유도 (이메일 리마인드)
   ▼
[재진단] 이전 진단과 나란히 비교. 점수 변화 · 해결된 문제 · 남은 문제
```

**핵심 설계 의도:** 무료 간이 진단에서 **점수와 한 문장 진단은 공개하고, 개선 방법은 잠근다.**
문제를 인지한 상태에서만 결제 동기가 생긴다. 다만 "치명적 문제 1개"는 실제로 유용한 걸 공개해야
신뢰가 생긴다 — 미끼용 빈껍데기를 주면 재방문이 끊긴다.

## 6. 기능 명세

### F1. 진단 대상 입력

**필수**
- 대상 유형 (A/B/C 택1) — 미선택 시 입력값으로 자동 추정 후 확인만 받는다
- 이름 (상호/사명/활동명)

**유형별 필수 추가**
- A: 지역(시·군·구 이상), 업종
- B: 업종 또는 사업 영역
- C: 전문 분야

**선택 (넣을수록 정확도가 올라간다고 UI에 명시)**
- 공식 홈페이지 URL
- 공식 SNS (복수)
- 언론 기사/인터뷰 링크 (복수)
- 기존 소개문 붙여넣기 (자유 텍스트)
- 첨부 자료 (PDF/이미지 — v1.5)

**동작 규칙**
- 입력이 이름 하나뿐이어도 진단은 진행된다. 대신 **자료 밀도(coverage)** 지표를 리포트 상단에 노출하고,
  낮으면 "이 진단의 신뢰구간이 넓다"고 명시한다.
- 사용자가 준 자료와 공개 웹 자료가 충돌하면 **공식 채널의 최신 정보를 우선**하되, 충돌 사실 자체를
  리포트의 '채널 간 불일치' 섹션에 그대로 기록한다.

### F2. 공개 자산 수집 (Asset Collection)

우선순위대로 수집하고, 각 자산에 출처 등급을 매긴다.

| 등급 | 출처 | 신뢰 가중치 |
|---|---|---|
| S | 공식 홈페이지 · 공식 소개 페이지 | 1.0 |
| A | 공식 SNS · 공식 채널 프로필 | 0.8 |
| B | 언론 기사 · 인터뷰 · 공공 기록(사업자 공시 등) | 0.7 |
| C | 플랫폼 소개 · 지도 프로필 · 리뷰 | 0.5 |
| D | 커뮤니티 · 블로그 후기 · 위키류 | 0.3 |

**수집 규칙**
- robots.txt와 각 사이트 약관을 준수한다. 차단된 페이지는 수집하지 않고 '수집 불가'로 기록한다.
- 검색 결과 스니펫만으로 결론 내리지 않는다. **실제 페이지 본문을 확인**한 자산만 등급을 부여한다.
- 각 자산에 `fetched_at`, `http_status`, `content_hash`, 본문 발췌를 저장한다 —
  재진단 시 변경 감지와 근거 재현에 쓴다.
- 수집 실패·미발견은 빈칸이 아니라 **'미확인'으로 명시적으로 기록**한다.

### F3. 검색 질문 세트 생성

대상별로 **8~12개** 질문을 생성한다. 아래 6개 범주를 고르게 섞는다.

| 범주 | 예시 (유형 A) | 예시 (유형 B) | 예시 (유형 C) |
|---|---|---|---|
| 정의형 | "○○ 베이커리는 어떤 곳이야?" | "○○는 뭐 하는 회사야?" | "○○ 강사는 어떤 사람이야?" |
| 추천형 | "성수동 브런치 추천해줘" | "국내 B2B 세금계산서 SaaS 추천" | "AI 실무 교육 강사 추천" |
| 비교형 | "○○랑 △△ 중 어디가 나아?" | "○○와 경쟁사 차이" | "○○ 강의랑 다른 강의 차이" |
| 최신형 | "○○ 요즘도 영업해?" | "최근 ○○ 소식" | "○○ 최근 활동" |
| 신뢰형 | "○○ 후기 어때?" | "○○ 믿을 만한 회사야?" | "○○한테 맡겨도 돼?" |
| 의도형 | "아이 데리고 갈 만한 성수동 카페" | "세금계산서 자동화 어떻게 해?" | "직원 30명 AI 교육 어떻게 시작해?" |

**의도형이 가장 중요하다.** 실제 사용자는 브랜드명을 모른 채 문제를 던진다.
여기서 후보에 오르는지가 GEO의 본질이다. 질문 세트의 최소 3개는 의도형이어야 한다.

각 질문마다 내부적으로 기록한다.
- 이 질문에서 대상이 후보로 잡힐 근거가 있는가
- 잡힌다면 어떤 출처가 인용될 가능성이 큰가
- 설명이 최신 상태로 묶일 가능성이 높은가

### F4. AI 응답 측정 (Probe)

**MVP 측정 방식 — 2트랙**

| 트랙 | 방법 | 측정하는 것 |
|---|---|---|
| 지식 트랙 | 웹검색 도구 **없이** LLM API에 질문 | 모델 파라미터에 대상이 남아 있는가 (장기 인지도) |
| 근거 트랙 | 웹검색 도구 **켜고** LLM API + Perplexity API에 질문 | 실시간 검색에서 후보로 잡히는가, 무엇이 인용되는가 |

각 probe에서 추출하는 값:
- `mentioned` — 대상이 답변에 등장했는가 (표기 흔들림 정규화 후 매칭)
- `position` — 답변 내 몇 번째로 호명됐는가
- `description_accuracy` — 답변 속 설명이 확인된 사실과 일치하는가 (일치/부분/불일치/환각)
- `cited_sources` — 인용된 URL 목록
- `raw_response` — 원문 보관 (근거 재현용)

**비결정성 대응:** 같은 질문을 **3회 반복 호출**하고 다수결로 `mentioned`를 확정한다.
3회 중 1~2회만 잡히면 '불안정 노출'로 별도 표기한다 — 이게 실제로 가장 흔한 상태다.

**측정하지 않는 것:** ChatGPT/Gemini 웹 UI를 브라우저 자동화로 조작하는 방식. 약관 위반이고
차단 시 서비스가 통째로 멈춘다. 리포트에는 "공식 API 기준 측정"임을 명시한다.

### F5. 7축 진단 채점

스킬 원본의 7개 축을 그대로 쓴다. 각 축은 `강함 / 보통 / 약함` 중 하나로 판정하고, 가중 합산해
**종합 점수 "AI 추천도" (0~100)** 를 낸다.

| # | 축 | 가중치 | 핵심 질문 | 주 판정 근거 |
|---|---|---:|---|---|
| 1 | 검색 존재감 | 20 | 이름·지역+업종·분야 키워드로 근거 페이지가 충분한가 | 자산 개수·등급, probe `mentioned` 비율 |
| 2 | 설명 정확도 | 20 | AI가 한 문장으로 정체성을 제대로 잡는가 | probe `description_accuracy` |
| 3 | AI 추천 질문 적합성 | 15 | 추천형·의도형 질문의 답변 후보에 드는가 | 추천형/의도형 probe의 `mentioned` |
| 4 | 채널 간 일관성 | 15 | 채널별 명칭·설명·링크가 같은 대상을 말하는가 | 자산 간 텍스트 대조 |
| 5 | 신뢰와 권위 | 12 | 검증 가능한 제3자 근거가 있는가 | B등급 이상 자산 수, 인용된 출처의 등급 |
| 6 | 정보 최신성 | 10 | 최근 6~12개월 내 갱신 흔적이 있는가 | 자산 `published_at`/갱신 흔적, 최신형 probe |
| 7 | 차별점 | 8 | 왜 이 대상을 추천해야 하는지가 문장으로 박혀 있는가 | 공식 채널 문구 분석, 비교형 probe |

**환산:** 강함 100 / 보통 60 / 약함 20 → 가중 평균.

| 등급 | 점수 | 해석 |
|---|---|---|
| A | 80~100 | AI가 안정적으로 찾고 정확히 설명한다 |
| B | 65~79 | 찾긴 하지만 추천 후보에선 자주 밀린다 |
| C | 50~64 | 이름은 알지만 정체성이 흐리다 |
| D | 35~49 | 조각 정보만 있고 설명이 어긋난다 |
| E | 0~34 | 사실상 존재하지 않는다 |

**판정보류 규칙:** 한 축의 근거 자산이 0개면 점수를 매기지 않고 `판정보류`로 표기한다.
판정보류 축은 가중치에서 제외하고 나머지로 정규화하되, 리포트 상단에 "N개 축 판정보류"를 명시한다.
**모르는 걸 '약함'으로 처리하지 않는다** — 근거 없음과 나쁨은 다르다.

### F6. 근거 규율 (제품의 핵심 방어선)

모든 서술은 세 라벨 중 하나를 달고 나간다. 이건 UI 뱃지로도 구분한다.

| 라벨 | 정의 | UI |
|---|---|---|
| **확인됨** | 공식 사이트·공식 SNS·직접 확인 가능한 기사/프로필에서 검증됨. 출처 URL 필수 | 파란 뱃지 + 링크 |
| **추정** | 공개 자료 밀도로 볼 때 AI가 그렇게 이해할 가능성이 높다는 해석 | 회색 뱃지 |
| **미확인** | 자료가 없거나 확인되지 않음 | 점선 뱃지 |

**금지 사항 (하드 룰).** 아래는 확인되지 않으면 **어떤 형태로도 생성하지 않는다.**
메뉴 · 가격 · 영업시간 · 경력 · 학력 · 수상 · 고객사 · 매출 · 실적 수치.
개선 문안(F7)에서도 마찬가지다 — 빈칸을 그럴듯하게 채우는 대신 `[여기에 실제 대표 메뉴를 넣으세요]`
같은 **플레이스홀더**로 남긴다. 이게 이 제품의 신뢰가 걸린 지점이다.

### F7. 개선 산출물 생성

진단으로 끝내지 않는다. 아래는 **전부 필수 산출물**이다.

| 산출물 | 사양 |
|---|---|
| 개선된 한 줄 소개 | 누구 / 무엇을 / 누구를 위해 / 어떤 강점으로 — 4요소를 최대한 담아 1문장 |
| 채널별 소개문 | ① 홈페이지 ② 인스타·유튜브 등 SNS ③ 링크드인·프로필 ④ 짧은 외부 소개용(보도자료·행사) |
| FAQ | 6~10개. 정의형·비교형·신뢰형·최신형·문제해결형 혼합 |
| AI 추천 질문 세트 | 6~10개. 실제 검색창에 넣을 법한 문장 |
| 7일 실행 계획 | Day 1 정체성 정리 → Day 2 소개문 통일 → Day 3 핵심 채널 수정 → Day 4 외부 신뢰 신호 → Day 5 FAQ/콘텐츠 → Day 6 추천 질문 대응 문서화 → Day 7 재검색·점검 |

각 산출물에 **복사 버튼**과 **글자 수 카운터**(채널별 제한 대응: 인스타 소개 150자 등)를 붙인다.

### F8. 리포트

출력 순서는 원본 스킬의 11개 섹션 계약을 그대로 지킨다. 이 순서는 임의가 아니라
"현재 상태 → 문제 → 원인 → 해결 → 실행"의 인지 순서다.

1. AI가 현재 이해하는 정체성 (확인됨/추정 분리, 3~6불릿)
2. 한 문장 진단
3. 항목별 진단표 (7축 × 현재상태·근거·판정·우선순위)
4. 채널별 정보 불일치 (홈페이지 / SNS / 기사·외부 / 플랫폼·지도)
5. 추천되기 어려운 이유 (3~5개)
6. 가장 먼저 고칠 문제 3가지 (무엇을 / 어디서 / 왜 먼저인지)
7. 개선된 한 줄 소개
8. 채널별 소개문
9. FAQ
10. AI가 추천할 수 있는 질문
11. 7일 실행 계획

**표 아래에는 반드시 1~2줄 해석을 붙인다.** 표만 던지고 끝내지 않는다.

**부가 기능:** PDF 내보내기 · 공개 공유 링크(만료 설정 가능) · 섹션별 복사 · 원본 probe 응답 열람(펼침)

### F9. 재진단과 추적

- 이전 진단을 부모로 참조하는 재진단을 생성한다.
- **비교 뷰:** 종합 점수 변화, 축별 변화, 해결된 문제, 새로 생긴 문제, 반영 확인된 문안.
- Day 7 이메일 리마인드로 재진단을 유도한다. (재진단은 유료 전환의 두 번째 관문이자 효능 증명 지점)
- Pro 구독은 주간 자동 재측정 + 변화 알림.

## 7. 데이터 모델 (초안)

```sql
-- 진단 1건
diagnoses (
  id, owner_id, parent_id,              -- parent_id: 재진단이면 이전 진단
  target_type,                          -- 'local' | 'company' | 'creator'
  target_name, region, industry,
  status,                               -- 'queued'|'collecting'|'probing'|'scoring'|'writing'|'done'|'failed'
  coverage_score,                       -- 자료 밀도 0~100
  total_score, grade,                   -- AI 추천도, A~E
  engine_version,                       -- 루브릭·프롬프트 버전 (재현성)
  created_at, completed_at
)

-- 수집한 공개 자산
diagnosis_assets (
  id, diagnosis_id,
  kind,                                 -- 'homepage'|'sns'|'press'|'platform'|'user_text'
  source_grade,                         -- 'S'|'A'|'B'|'C'|'D'
  url, title, excerpt,
  http_status, content_hash, fetched_at, published_at
)

-- 생성한 질문
diagnosis_queries (
  id, diagnosis_id, category, text       -- category: definition|recommend|compare|recent|trust|intent
)

-- 질문별 AI 응답 측정
diagnosis_probes (
  id, query_id, engine, track,           -- track: 'knowledge'|'grounded'
  attempt,                               -- 1..3 (비결정성 대응)
  mentioned, position,
  description_accuracy,                  -- 'match'|'partial'|'mismatch'|'hallucinated'
  cited_sources jsonb, raw_response, ran_at
)

-- 축별 판정
diagnosis_findings (
  id, diagnosis_id, axis,                -- 7축
  verdict,                               -- 'strong'|'normal'|'weak'|'unrated'
  priority,                              -- 1..N
  statement, evidence jsonb              -- evidence: [{label, url, quote}]
)

-- 생성한 개선 산출물
diagnosis_outputs (
  id, diagnosis_id, kind,                -- 'one_liner'|'channel_copy'|'faq'|'questions'|'plan7'
  payload jsonb
)

-- 7일 계획 진행 체크
diagnosis_plan_progress (id, diagnosis_id, day, done, done_at)
```

**설계 의도**
- `engine_version`을 남긴다. 루브릭을 고치면 과거 진단의 점수 의미가 달라진다 — 버전 없이 비교하면 거짓말이 된다.
- `raw_response`를 보관한다. "AI가 이렇게 말했다"는 주장의 근거이자, 분쟁 시 방어 자료다.
- `content_hash`로 재진단 때 실제로 채널이 바뀌었는지 판정한다.

## 8. 시스템 아키텍처 (초안)

```
[Next.js App Router] ── 랜딩 · 입력 폼 · 리포트 · 공유 페이지
        │
        ├── POST /api/diagnoses          진단 생성 → 큐 적재
        ├── GET  /api/diagnoses/:id      상태 폴링 (SSE 또는 폴링)
        │
[Job Worker]  진단 파이프라인 (비동기, 3~7분)
   ① collect  공개 자산 수집 (검색 API + 페이지 페치 + robots 준수)
   ② query    질문 세트 생성 (LLM)
   ③ probe    2트랙 × N질문 × 3회 측정 (LLM API + Perplexity API), 병렬
   ④ score    7축 채점 (룰 + LLM 판정 하이브리드)
   ⑤ write    11섹션 리포트 + 개선 문안 생성 (LLM)
   ⑥ verify   자체 검증 게이트 — 근거 없는 사실 서술·깨진 링크 검출 시 재생성
        │
[Postgres]  진단·자산·probe·판정·산출물
[Object Storage]  PDF, 페이지 스냅샷
```

**기술 선택 (ai-nocutnews 경험 재사용)**
- Next.js App Router + Postgres(Supabase) — 이미 팀이 운영해본 스택. 학습비용 0.
- LLM은 OpenRouter 경유로 모델 교체 가능하게 둔다. **비추론 모델을 기본으로 쓴다** — ingest에서
  이미 겪었듯 추론 모델은 토큰을 추론에 소모해 구조화 출력이 잘린다.
- 파이프라인은 **단계별로 중단·재개 가능**해야 한다. 5단계 중 4단계에서 실패했다고 처음부터
  다시 돌리면 비용이 그대로 두 배다.

**⑥ verify 게이트가 핵심이다.** 생성 결과를 그대로 사용자에게 내보내지 않는다.
- 사실 서술인데 `evidence`가 비어 있으면 → 해당 문장 삭제 또는 '미확인' 라벨 강제
- 금지 항목(가격·경력·수상 등)이 근거 없이 등장하면 → 플레이스홀더로 치환
- 인용 URL HEAD 체크 → 4xx/5xx면 근거에서 제외
- 이 게이트 통과율을 내부 품질 지표로 상시 추적한다.

## 9. 화면 명세 (MVP)

| # | 화면 | 핵심 요소 |
|---|---|---|
| S1 | 랜딩 | 문제 제기 카피, 상호+지역 입력 1줄, 샘플 리포트 보기 |
| S2 | 유형 선택 | 3개 카드. 입력값으로 추정되면 프리셀렉트 |

| S5 | 리포트 | 11섹션. 좌측 목차 고정, 근거 뱃지, 섹션 복사 버튼 |
| S6 | 7일 계획 | 체크리스트. 진행률. Day 7에 재진단 CTA |
| S7 | 비교 뷰 | 이전/이번 진단 나란히. 점수 델타 강조 |
| S8 | 공유 페이지 | 읽기 전용. 내부 메모·원본 응답 숨김. 만료일 설정 |
| S9 | 마이페이지 | 진단 목록, 결제 내역, 구독 관리 |

**S4를 대충 만들면 안 된다.** 3~7분은 웹에서 매우 긴 시간이다. "수집 중"만 도는 스피너면 이탈한다.
"공식 홈페이지 확인 완료 → 네이버 플레이스 확인 중 → 질문 11개 생성 완료" 처럼 실제 진행을 보여주고,
백그라운드 전환 + 완료 시 이메일 발송을 지원한다.

| 품질 | verify 게이트 1차 통과율 | ≥ 85% |
| 품질 | 사실 오류 신고 건수 | 진단 100건당 1건 미만 |
| 운영 | 진단 완료 P90 소요시간 | ≤ 10분 |
| 운영 | 진단 실패율 | ≤ 3% |
| 원가 | 진단 1건 평균 원가 | ≤ 3,000원 |

## 12. 품질 기준 (리포트 톤)

원본 스킬의 규율을 제품 차원의 검수 기준으로 승격한다.

- 실무형으로 쓴다. 허세 금지.
- 애매하면 애매하다고 쓴다. **자료가 빈약할수록 더 단정하지 말고 더 정확하게 쓴다.**
- 판단과 사실을 섞지 않는다.
- 표 아래에는 반드시 해석 1~2줄.
- 중요한 사실은 가능하면 2개 이상 교차 확인한다.
- 공식 채널이 있으면 공식 채널 링크를 우선 인용한다.
- 근거 URL은 해당 문장 끝에 붙인다.

## 13. 리스크와 대응

### 13.1 환각 — 최대 리스크
지어낸 메뉴·경력·수상이 리포트에 실리면 제품 신뢰가 한 번에 무너진다. 고객이 그걸 자기 채널에
그대로 올리면 피해가 고객에게 전이된다.
> **대응:** F6 하드 룰 + ⑥ verify 게이트 + 금지 항목 플레이스홀더 강제 + 출시 전 50건 수동 감사.
> 사실 오류 신고 채널을 리포트 안에 상시 노출하고, 신고 건은 48시간 내 검토·정정한다.

### 13.2 측정 비결정성
같은 질문에 매번 다른 답이 나온다. "어제는 됐는데 오늘은 안 된다"는 클레임이 반드시 온다.
> **대응:** 3회 반복 다수결 + '불안정 노출' 별도 표기 + 측정 시각·모델·버전 명시 +
> "생성형 답변은 시점·모델에 따라 달라진다"는 고지문 상단 고정.

### 13.3 수집 정합성·약관
검색 API 비용, robots 차단, 플랫폼 약관(지도·리뷰 크롤링) 문제.
> **대응:** 공식 API 우선. robots 준수. 차단 페이지는 '수집 불가'로 남기고 우회하지 않는다.
> 플랫폼별 허용 범위는 법무 검토 항목으로 [16. 오픈 이슈]에 올린다.

### 13.4 개인정보와 명예
유형 C는 실명 개인이 대상이다. 제3자가 타인을 임의 진단하고 그 리포트를 공개하는 시나리오가
가능한 구조면 문제가 된다.
> **대응:** ① 진단 요청 시 "본인 또는 권한 있는 담당자" 확인 체크 ② 유형 C 리포트의 **외부 공유 링크는
> 본인 이메일 인증 후에만 생성** ③ 리포트에 부정적 인물 평가 문장을 생성하지 않는다(채널·문서 상태만
> 평가하고 사람을 평가하지 않는다) ④ 삭제 요청 시 즉시 파기.

### 13.5 원가 폭주
질문 12개 × 2트랙 × 3회 = 72회 LLM 호출 + 페이지 수십 건 페치. 방치하면 건당 원가가 가격을 넘는다.
> **대응:** 무료 간이는 질문 4개·1트랙·1회로 축소. 정밀 진단은 단계별 상한과 타임아웃.
> 동일 대상 24시간 내 재요청은 캐시 재사용. 원가는 진단마다 기록해 상시 모니터링.

### 13.6 "그래서 뭐" 리스크
점수만 보고 "그래서 뭘 하라고?"로 끝나는 리포트는 재구매가 없다.
> **대응:** 이건 리스크가 아니라 제품 정의다. F7 산출물이 **필수**인 이유가 여기 있다.
> 리포트 분량의 절반 이상이 '고칠 문장'이어야 한다.

### 13.7 과대광고 규제
"AI 1위 노출 보장" 류 표현은 표시광고법 이슈가 된다.
> **대응:** 보장 표현 금지를 카피 가이드에 명문화. 리포트·랜딩 모두 "추정 진단"임을 명시.

## 15. 원가 가정

정밀 진단 1건 기준 (검증 필요, M0에서 실측):

| 항목 | 수량 | 비고 |
|---|---:|---|
| 질문 생성 | 1회 | |
| Probe | 12질문 × 2트랙 × 3회 = 72회 | 가장 큰 비용. 답변 길이 제한 필수 |
| 페이지 페치 | 20~40건 | 검색 API + 본문 추출 |
| 채점 | 7~14회 | 축별 LLM 판정 |
| 리포트 생성 | 3~5회 | 섹션 분할 생성 |
| verify | 1~2회 + 링크 HEAD 체크 | |

**목표: 건당 3,000원 이하.** 초과 시 우선 축소 순서는 ① probe 반복 3회 → 2회 ② 질문 12개 → 8개
③ 지식 트랙 축소. **verify 게이트는 절대 줄이지 않는다** — 여기가 제품의 신뢰다.
